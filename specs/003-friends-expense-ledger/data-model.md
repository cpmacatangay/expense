# Data Model: Salo Friends Expense Ledger

**Feature**: `003-friends-expense-ledger` | **Date**: 2026-11-17

The database is the authority for money, access, and history. The browser may preview shares, but
only the server writes them. All amounts are integer centavos in `bigint`; floating point is never
used for money.

## Conventions

- Primary keys are `uuid` generated by `gen_random_uuid()`.
- Timestamps are `timestamptz`; dates are `date` in Asia/Manila.
- Emails are stored as entered but compared with `lower(email)`.
- Soft-deleted expenses keep their row and history; every read filters `deleted_at is null`.
- No table is writable directly by `authenticated`; writes go through RPCs.
- All RPCs use `security definer`, `set search_path = public, pg_temp`, and an explicit
  `auth.uid()` check.

## Enums

```sql
create type public.person_status as enum ('pending', 'active', 'former');
```

No expense status enum: an expense is live or soft-deleted. No settlement status enum: a payment is
active or undone.

## Tables

### `public.people`

One row per Google identity email or per named placeholder. Replaces `group_adults`.
Self-service Google sign-up creates a row on first sign-in with no expenses attached. A name added
to an expense creates a placeholder with no email until the person claims the expense link.

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `email` | text | nullable, 3–254 chars when present, unique on `lower(email)` |
| `display_name` | text | not null, 1–50 chars |
| `profile_id` | uuid | nullable, unique, FK `profiles(id)` on delete set null |
| `status` | `person_status` | not null, default `pending` |
| `payment_qr_path` | text | nullable, ≤400 chars, must start with `id::text || '/'` |
| `payment_qr_label` | text | nullable, 1–40 chars |
| `payment_qr_updated_at` | timestamptz | nullable |
| `created_by_person_id` | uuid | nullable FK `people(id)` on delete set null |
| `created_at` | timestamptz | not null default now() |
| `updated_at` | timestamptz | not null default now() |

Constraints:

```sql
check (char_length(display_name) between 1 and 50)
check (email is null or char_length(email) between 3 and 254)
check (
  (status = 'pending' and profile_id is null)
  or (status = 'active' and profile_id is not null)
  or (status = 'former' and profile_id is null)
)
check (payment_qr_path is null or payment_qr_path like id::text || '/%')
```

Indexes: `unique (lower(email))`, `unique (profile_id) where profile_id is not null`,
`(status)`, `(created_by_person_id)`.

The retained `profiles` table gets `create index profiles_email_lower_idx on public.profiles
(lower(email))` so a returning account can be relinked. It is not unique; Supabase Auth is the
identity authority, and the person row enforces one identity per account email.

A `former` person keeps past expenses and payments. If the same email signs in again,
`claim_people_for_me` may relink the row and return it to `active`. A `before delete` trigger on
`profiles` sets every linked person to `status = 'former'` and `profile_id = null` in one update, so
the status check passes before the foreign key action. A former person can remain a participant on a
live expense; the active counterpart can still mark a resulting debt paid, but the former person
cannot sign in or undo it.

### `public.expenses`

| Column | Type | Rules |
|---|---|---|
| `id` | uuid | PK |
| `description` | text | not null, 1–120 chars |
| `expense_date` | date | not null, default Manila today |
| `payer_person_id` | uuid | not null FK `people(id)` on delete restrict |
| `created_by_person_id` | uuid | not null FK `people(id)` on delete restrict |
| `total_centavos` | bigint | not null, `> 0` for a saved expense |
| `version` | integer | not null default 1, `> 0` |

| `share_expires_at` | timestamptz | nullable; 7 days after the token was created |

Rules enforced by `save_expense` and a deferred integrity trigger:

- The payer is a participant.
- The creator is a participant.

- Every item belongs to a participant.

`(expense_date desc, created_at desc) where deleted_at is null`,
`(payer_person_id) where deleted_at is null`, `(created_by_person_id)`.

### `public.expense_coverage`

| Column | Type | Rules |
|---|---|---|
| `expense_id` | uuid | not null |
| `covered_person_id` | uuid | not null |
| `coverer_person_id` | uuid | not null |
| PK | | `(expense_id, covered_person_id)` |

Composite FKs to `expense_people` for both people. A row means the coverer absorbs the covered
person's full share.

Trigger `validate_expense_coverage` rejects:

- covered = coverer
- covered = the expense payer
- covered already appears as a coverer in the same expense (chain)
- coverer already appears as covered in the same expense (chain)
- either person not on the expense (also blocked by the composite FK)

A coverer may cover several people. Deleting a coverage row recalculates on the next save; the save
RPC replaces the whole set atomically.

### `public.expense_shares`

| Column | Type | Rules |
|---|---|---|
| `expense_id` | uuid | not null |
| `person_id` | uuid | not null |
| `items_centavos` | bigint | not null, `>= 0` — own assigned items |
| `covered_centavos` | bigint | not null, `>= 0` — items this person covers |
| `owed_centavos` | bigint | not null, `>= 0` — amount owed to the payer |
| `covered_by_person_id` | uuid | nullable FK `people(id)` |
| PK | | `(expense_id, person_id)` |

Check:

```sql
check (covered_by_person_id is distinct from person_id)
check (covered_by_person_id is null
       and owed_centavos = items_centavos + covered_centavos
       or covered_by_person_id is not null
       and owed_centavos = 0
       and covered_centavos = 0)
```

Indexes: `(person_id, expense_id)`, `(expense_id)`.

A deferred trigger verifies `sum(owed_centavos) = expenses.total_centavos`.

### Expense share links

A share link is stored on the expense itself: `share_token` (raw, unguessable 48-character hex) and
`share_expires_at` (7 days after creation). There is no separate invitation table.

- `create_expense_share(expense_id, refresh?)` — creator or payer only. Reuses a valid token, or
  rotates it and starts a new 7-day window.
- `expense_share_preview(token)` — any signed-in caller with a valid token. Returns the expense
  summary, whether the caller is already a participant, and the open names (`status = 'pending'`
  and `profile_id is null`). It never returns items, shares, or email addresses.
- `claim_expense_share(token, person_id)` — any signed-in caller with a valid token. Locks the
  expense, validates that the chosen person is an open name on it, then merges that placeholder
  into the caller's account person: items, coverage, shares, payer/creator references, payments,
  and events are rewritten, the placeholder is deleted, and an `updated` event is recorded.
- The placeholder merge keeps one `people` row per account. If the caller already has a share on
  the expense, the claim returns `alreadyClaimed: true` instead of creating a duplicate.
- Expired or refreshed tokens are refused with “This link is no longer available”. A token that is
  already claimed cannot be claimed again.
- No email is sent. `add_person(name)` only creates or reuses a named placeholder owned by the
  caller; `people_for_me` returns joined/not-joined status and no email fields.

## Money Rules

Given participants `P`, payer `a ∈ P`, items `I`, and coverage `C`:

1. `gross[p] = sum(amount of items assigned to p)`, integer centavos.
2. `total = sum(gross) = sum(item amounts)`; total must be `> 0`.
3. Coverage is one level. `coveredSet` are people with a coverer; `covererSet` are people covering
   someone. The sets are disjoint.
4. `owed[p] = 0` if `p ∈ coveredSet`; otherwise
   `owed[p] = gross[p] + sum(gross[c] for c where coverer[c] = p)`.
5. `sum(owed) = total`; otherwise the save fails.
6. For every `p ∈ P`, `p ≠ a`, with `owed[p] > 0`: `p` owes `a` that amount.
7. Every participant gets an `expense_shares` row, including zero rows, so the detail can show
   “covered by” and “no items”.
8. No division occurs, so there is no remainder allocation. An input amount with more than two
   decimal places is rejected or rounded at entry before it reaches the server.

Worked example:

- Items: A ₱300, B ₱200, C ₱100. Payer A. B covers C.
- `gross = {A:300, B:200, C:100}`; `total = 600`.
- `owed = {A:300, B:300, C:0}`.
- Debt: B owes A ₱300. C owes nothing.

Payer covers C:

- `owed = {A:400, B:200, C:0}`.
- Debt: B owes A ₱200. The payer absorbs C's share.

## Balance Computation

For the viewer `me`:

```sql
debt_edges as (
  select s.person_id as debtor, e.payer_person_id as creditor, s.owed_centavos as amount
  from expense_shares s
  join expenses e on e.id = s.expense_id
  where e.deleted_at is null
    and s.owed_centavos > 0
    and s.person_id <> e.payer_person_id
    and (s.person_id = me or e.payer_person_id = me)
),
payment_edges as (
  select from_person_id as payer, to_person_id as payee, amount_centavos
  from payments
  where undone_at is null
    and (from_person_id = me or to_person_id = me)
)
```

For each other person:

- `debt_out = sum(amount where debtor = me and creditor = other)`
- `debt_in = sum(amount where creditor = me and debtor = other)`
- `paid_out = sum(amount where payer = me and payee = other)`
- `paid_in = sum(amount where payer = other and payee = me)`
- `net = debt_out - debt_in - paid_out + paid_in`

Positive `net` means “you owe them”. Negative means “they owe you”. Zero is settled and hidden.
Totals are the sum of positive and negative nets. An edit or delete that makes payments exceed the
shares flips the sign, which is the required direction reversal.

## Coverage Examples

| Case | Allowed | Result |
|---|---|---|
| A pays, B covers C | yes | B owes A its own plus C |
| A pays and covers C | yes | A absorbs C; no debt from C |
| A pays, B covers C, C covers B | no | loop |
| A pays, B covers C, D covers B | no | chain |
| A pays and is covered by B | no | payer cannot be covered |
| B covers B | no | self |
| B covers C and D | yes | B owes for C and D |
| B covers C, then C removed | yes | coverage row is removed with the participant |

## Access Helpers

```sql
current_person_id() -> uuid
is_expense_participant(expense_id uuid) -> boolean
can_edit_expense(expense_id uuid) -> boolean
can_view_person(person_id uuid) -> boolean
```

`can_view_person` is true for self, for anyone sharing an active expense, or for anyone with a
payment history together. This keeps QR access after a settled debt and blocks unrelated people.

`can_edit_expense` is true for the creator or payer while the expense is not deleted.

`expense_events` deliberately allows participants to read a deleted expense's deletion event, while
the detail RPC returns not found. No other table exposes deleted expenses. There is no invitation
table: share tokens live on `expenses` and are reachable only through the security-definer RPCs.

Direct privileges: `revoke all on ... from anon, authenticated`; grant `select` only where a policy
exists. RPCs are granted to `authenticated` individually.

## State Transitions

**Person**: `pending → active` (expense link claimed, or a returning account relinked by email),
`active → former` (account deleted), `former → active` (same Google email signs in again). A claimed
placeholder is merged into the account person and hard-deleted; a person is never deleted while
referenced.

**Expense share link**: created on first share, reused until `share_expires_at`, then `expired`, or
rotated by the creator/payer. Claiming a name does not expire the link for the other open names.

**Expense**: `live v1 → live vN` on each save, `live → deleted` terminal. A stale version is
rejected. A deleted expense cannot be restored.

**Payment**: `active → undone` terminal. A later mark creates a new row. No edits to amount or
direction.

## Validation Rules

- Account email: optional on a person row, trimmed, lowercased for comparison, ≤254 characters.
- Display name: 1–50 characters, trimmed.
- Description: 1–120 characters, trimmed.
- Date: valid date; defaults to Manila today; no restriction on past or future.
- Participants: 2–12, unique, all people rows exist, creator and payer included.
- Items: at least one; name 1–120; amount positive integer centavos; assignee a participant.
- Coverage: one coverer per covered person; all rules above; no coverage for the payer.
- Version: must equal the current version for updates; new expenses start at 1.
- Delete: creator or payer only; confirmation names the description.
- Mark paid: current net must be non-zero; amount is the absolute net; marker is a pair member.
- Undo: either pair member; only an active payment; one undo.
- Account deletion: both ledger totals must be zero; the Edge Function calls `can_delete_account`
  and then deletes the auth user with the service role. Past expenses keep the display name.
- Share link: creator or payer only; one token per expense; 7-day window; refresh rotates the
  token; preview never returns items, shares, or email addresses.
- Claim: signed-in caller; token live; chosen person is an open name on that expense; if the caller
  is already on the expense, return `alreadyClaimed`; otherwise merge and log an update event.
- Sign-in: Google only. No email is sent for authentication or invites; no SMTP or sending domain is
  required.
- QR: PNG/JPEG ≤2 MB; label ≤40; path owned by the person.

## Storage

Bucket `payment-qr` remains private with a 2 MB limit and PNG/JPEG MIME allowlist.

Object path: `{person_id}/{timestamp}.{ext}`.

Policies:

- SELECT: `bucket_id = 'payment-qr' and can_view_person(((storage.foldername(name))[1])::uuid)`
- INSERT/UPDATE/DELETE: `bucket_id = 'payment-qr' and ((storage.foldername(name))[1])::uuid = current_person_id()`

The client requests a 60-second signed URL. No public URL is stored or returned.
