# Contract: Realtime and Sync

**Feature**: `002-salo-pwa` | **Consumers**: outing editor, ledger, activity, draft publishing

## Source of Truth

The shared backend is authoritative. IndexedDB is a cache and a private-draft store. A client must
never treat a cached row as permission to write.

## Write Protocol

Every shared outing write carries the outing's `version`.

1. Client loads an outing at version `v`.
2. Client sends the mutation with `expectedVersion = v`.
3. Server checks the current version:
   - equal: apply the mutation, increment to `v + 1`, return the new row;
   - different: reject with `STALE_WRITE`, return the current row.
4. On `STALE_WRITE`, the client refreshes the outing and shows "Someone changed this outing" with the
   latest data. The member may retry.

No last-write-wins. No automatic field merge in v1.

## Realtime Channels

Subscribe per active group after the group is opened:

| Channel | Events |
|---|---|
| `group:{id}:outings` | outing created, updated, finalized, reopened, published |
| `group:{id}:items` | item inserted, updated, deleted |
| `group:{id}:shares` | shares written or replaced |
| `group:{id}:settlements` | settlement recorded, confirmed, declined, voided |
| `group:{id}:activity` | new activity event |
| `group:{id}:members` | adult invited, claimed, removed, ownership transferred |

Rules:
- RLS applies to realtime payloads; a member never receives another group's events.
- A private draft emits only to its author and the owner.
- On reconnect, the client refetches the current group state; realtime is an enhancement, not the only
  source.
- If realtime is unavailable, the client falls back to refresh-on-open and pull-to-refresh.

## Private Drafts

A private draft is local-first:

1. The draft is written to `privateDrafts` in IndexedDB.
2. When online, it is mirrored to the server as an outing with `status = private_draft`.
3. Only the author and the group owner can read the mirrored draft.
4. The author or owner may publish it:
   - status becomes `draft`;
   - all active members can see it;
   - the local draft records the mirrored outing id and publish result.
5. Publishing is idempotent. A retry returns the same outing and does not create a duplicate.
6. Other members cannot see the draft, receive realtime events for it, or edit it.

## Offline Behavior

| Capability | Offline |
|---|---|
| Open cached groups and outings | yes |
| Read finalized shares and settlements | yes |
| Create/edit a private draft | yes |
| Publish a draft | no; requires connection |
| Edit a shared draft | no; requires connection |
| Finalize or reopen | no; requires connection |
| Record/confirm/decline a settlement | no; requires connection |
| Receive live updates | no; refetch on reconnect |

The UI must show a clear offline banner and disable shared-write actions with an explanation. A
private draft remains editable offline.

## Retry and Idempotency

- Online writes carry an idempotency key generated by the client.
- A retry of the same write returns the original result.
- A failed publish does not create a second outing.
- A failed finalization does not write partial shares.
- A failed settlement decision leaves the settlement pending and can be retried.

## State Display

The app must distinguish:

- **Online**: connected and writes enabled.
- **Offline**: cached reads only; shared writes disabled.
- **Connecting**: trying to re-establish.
- **Syncing**: a write is in flight.
- **Published**: a draft is shared.
- **Private draft**: local or author/owner-only.
- **Stale**: the loaded outing is older than the server; refresh needed.
- **Error**: a readable failure with retry.

## Conflict Examples

- Two members edit the same item. The second save receives `STALE_WRITE`; the item shows the latest
  value and the second member retries.
- Two members try to finalize. Only the owner can finalize; a second attempt receives a state error
  and reloads the finalized snapshot.
- A member publishes a private draft twice. The second publish is idempotent and opens the existing
  shared draft.
- A recipient confirms a settlement after the payer voided it. The confirmation is rejected because
  the settlement is no longer pending; the recipient sees the void.
